# DataSync Studio

一个仿 Navicat 的 macOS 数据库同步工具，支持 **MySQL** 与 **PostgreSQL**。

> **只支持同类型同步**：MySQL → MySQL、PostgreSQL → PostgreSQL。
> 跨类型（MySQL → PostgreSQL 或反向）会被明确拒绝——两者的类型、生成表达式、
> 视图 SQL 都不同，机械转换无法保证正确。界面上目标连接会按源连接的类型自动过滤。

- **连接管理**：保存 / 编辑 / 测试 / 删除连接，密码加密存储
- **库表浏览**：每个库下分「表 / 视图 / 查询」三组；表数据支持服务端搜索条件、列头排序、可拖拽列宽、单击单元格直接改数据
- **查询（自定义 SQL）**：查询就是磁盘上的 `.sql` 文件，可直接用任何编辑器打开、进 Git、拷贝分享；内置 SQL 控制台可执行多语句并查看结果
- **标签页**：多个对象可同时打开，右键标签可「关闭 / 关闭其他 / 全部关闭」，中键单击也可关闭
- **表级操作**：右键表可「编辑字段 / 重命名 / 删除表」；⌘/Ctrl 点选、Shift 范围选后可批量删除
- **结构同步**：对比两个库的表 / 列 / 索引 / 外键 / 主键差异，勾选后生成 DDL 并执行
- **数据同步**：按主键匹配，计算新增 / 修改 / 删除行，批量生成 DML 并事务化执行
- **Excel 导入 / 导出**：右键表 → 导入 → 从 Excel 导入；右键表 → 导出 → 导出 Excel

技术栈：**Tauri 2 + React 19 + TypeScript + Rust (sqlx)**。Rust 侧负责全部数据库通信与 SQL 生成，前端只做展示与选择。

## 快速开始

```bash
# 依赖安装（首次）
pnpm install

# 开发模式（会打开应用窗口）
pnpm tauri dev

# 打包 .app，产物在 src-tauri/target/release/bundle/macos/
pnpm tauri build

# 再打一个 DMG 安装包（含 /Applications 快捷方式）
./scripts/package-dmg.sh
```

产物：

```
src-tauri/target/release/bundle/macos/DataSync Studio.app      # 可直接运行
src-tauri/target/release/bundle/dmg/DataSync Studio_0.1.0_arm64.dmg
```

> Tauri 自带的 `tauri build --bundles dmg` 会用 Finder AppleScript 排版窗口，
> 在没有可控 Finder 的会话（远程 shell、CI、沙箱）里必然失败。
> `scripts/package-dmg.sh` 改用 `hdiutil`，不依赖 Finder，因此到处都能跑。

> 如果本机 pnpm / cargo 的全局缓存目录不可写，可先 `source dev-env.sh`，
> 它会把所有工具缓存重定向到仓库内的 `.cache/`。

### 前置要求

- macOS（Apple Silicon 或 Intel）
- Node.js 18+ / pnpm
- Rust 稳定版 + Xcode Command Line Tools

## 使用流程

> **所有会等待数据库的操作都有明确的加载反馈**。首次加载时显示转圈与说明文字；已有内容时显示
> 半透明浮层，**旧数据保持可见只是变暗**——等待时把屏幕清空会让人分不清「在加载」和「卡死了」，
> 而窗口卡死时用户的第一反应就是强退。


### 1. 新建连接

工具栏「新建连接」→ 选择 MySQL / PostgreSQL → 填写主机、端口、用户名、密码、数据库。

- 密码使用 **AES-256-GCM** 加密后保存在配置目录，主密钥存放在 **macOS 钥匙串**。
  钥匙串不可用时回退为配置目录下的 `.masterkey`（0600 权限）。
- 「测试连接」会在保存前验证连通性并显示服务端版本。

### 2. 连接与浏览

左侧双击连接建立会话，展开后即可浏览模式与表。点击表名打开数据浏览标签页。

### 3. 表级操作（右键表）

| 操作 | 说明 |
| --- | --- |
| 浏览数据 | 打开只读数据网格 |
| 新建表 | 右键库节点或「表」分组 →「新建表…」：表名 + 字段 + 勾选主键，可预览 `CREATE TABLE` 后再执行 |
| 编辑表 | 三个页签：**表字段**、**表索引**、**外键**；可预览 SQL 后再应用 |
| 重命名 | 重命名表（MySQL `RENAME TABLE` / PostgreSQL `ALTER TABLE ... RENAME TO`） |
| 删除表 | 单表或批量删除，删除前会先生成计划并展示要执行的语句 |
| 导入 | 从 Excel 导入（xlsx / xlsm / xlsb / xls / ods） |
| 导出 | 导出 Excel（xlsx）：选择列、重命名表头、调整列顺序、设置工作表名与行数上限 |

#### 新建表

右键库节点或「表」分组 →「新建表…」。填表名、加字段、勾选主键列即可；索引与外键建好之后再用
「编辑表」添加。

生成的 `CREATE TABLE` **复用结构同步建新表用的同一个生成器**，所以手工建的表和同步建的表完全一致
（MySQL 把索引内联、PostgreSQL 拆成独立 `CREATE INDEX`）。表名重复、或主键指向不存在的字段，
都会在发出请求前就报错。

#### 表字段

几个刻意为之的细节：

- **字段改名走 `RENAME COLUMN`，不会丢数据。** 设计器把改名作为独立信息上报，后端先在
  「当前结构」上套用改名再对比，因此不会退化成「删列 + 加列」。MySQL 用 `CHANGE`（8.0 才有
  `RENAME COLUMN`），PostgreSQL 用 `RENAME COLUMN`。
- **表编辑器永远不能建表或删表。** 后端只保留 `add_column` / `drop_column` /
  `modify_column` / `column_comment` / `create_index` / `drop_index` 这几类语句，
  即使对比得出别的结论也会被过滤掉。
- **删表会自动解除指向它的外键**，包括位于未选中表上的外键；所有外键解除都排在删表之前。
  若仍有视图依赖这些表，会明确列出视图名而不做级联删除。
- **多选范围**限定在同一个连接 + 同一个库内（批量操作的可作用范围）。
- 所有表级操作同样走事务化执行，失败即回滚（PostgreSQL）。

#### 表索引

列出当前二级索引，可增删、改列与列顺序、切换唯一约束。主键不在其中（它是「表字段」页签里的
主键，单独一行只读展示）。

两个来自真机行为的处理：

- **外键自动创建的索引不能删。** MySQL 会为外键建一个同名索引，用户把它删掉时服务端会报
  `Cannot drop index ... needed in a foreign key constraint`。工具认出「每个外键保留一个支撑
  索引」（按 MySQL 的规则：外键的列是索引列的前缀），把那个索引标成只读并显示「外键」标签；
  即使调用方把它从列表里去掉，规划器也会保留它并说明原因。
- **MySQL 上「删旧索引 + 建新索引」必须在同一条 `ALTER TABLE` 里。** MySQL 在语句结束时
  才校验外键，分成两条语句时先执行的 `DROP INDEX` 会因为新索引还不存在而被拒绝。所以
  MySQL 的索引变更会合并成一条 `ALTER TABLE t DROP INDEX a, ADD INDEX b (...)`；
  PostgreSQL 不受此限，仍是独立的 `CREATE INDEX` / `DROP INDEX`。

改了字段名时，引用它的索引列会一并改写，避免生成一条引用已不存在字段的语句。

#### 外键

按「字段对」编辑：每对是 `本表字段 → 引用字段`，两端数量必须一致（两个引擎都要求），
不一致会在提交前直接指出。还可以设置引用模式与表、`ON DELETE` / `ON UPDATE` 动作
（`NO ACTION` / `CASCADE` / `SET NULL` / `RESTRICT` / `SET DEFAULT`）。引用模式留空表示
与当前表同一个模式。

和索引页签一样，**没提交外键列表时不会碰外键**，所以在表字段页签改列不会误删外键。

### 4. 查询（自定义 SQL）

每个数据库下有 **表 / 视图 / 查询** 三个分组。

**查询是「先写后存」，不是「先建后写」**：先在左侧选中一个库，上方工具栏的 **查询** 按钮就可用，
点它打开一个**临时查询**窗口——写、执行，什么都不会落盘。只有在点「保存到文件…」并起名之后，
它才会作为 `.sql` 文件出现在左侧「查询」分组里。

> 这样设计的理由：很多时候只是临时跑一条 SQL 看看，不该在查询目录里留下垃圾文件。
> 树的「查询」分组是**已保存查询的只读清单**，不提供「新建」入口。

**查询就是磁盘上的 `.sql` 文件**，不是存在应用内部。目录结构可读，可以直接用任何编辑器打开、
放进版本控制、拷给别人：

```
~/Library/Application Support/com.datasync.studio/queries/
  方塘线上mysql/
    .connection          # 记录连接 id，所以改连接名不会丢失查询
    datasync1/
      导出数据.sql
      预存统计.sql
```

> 文件夹按连接名命名（人看着舒服），靠里面的 `.connection` 标记文件与连接绑定——
> 所以**改连接名之后原有查询仍然找得到**，只是文件夹名会显得旧一点。
> 右键查询或分组可以「在访达中打开查询目录」。

**语法高亮**：关键字、字符串、注释、数字、函数调用分色显示。做法是「透明 textarea + 底层高亮层」
叠层——textarea 负责光标、选区与输入，下面的 `<pre>` 负责颜色；两层共用同一份样式对象
（字体、行高、内边距、换行方式），否则颜色会和字符错位。

**分析执行计划**：点「分析执行计划」对每条语句生成执行计划，逐条展示。
用的是 `EXPLAIN` 而**不是 `EXPLAIN ANALYZE`**——后者会**真的执行**语句，对 `UPDATE`/`DELETE`
意味着改数据。不带 ANALYZE 的计划仍然能看到索引选择与连接顺序，这正是这个按钮要回答的问题。
不支持计划的语句类型会被标为「不支持」而不是报错。

**语法检查是自动的**，分两层，都不需要点任何按钮：

1. **就地检查（即时）**：未闭合的引号、未闭合的块注释、括号不配对，边打边标——不需要联网。
2. **服务端检查（停止输入 700ms 后）**：用 `PREPARE` 让服务端解析并校验每条语句，**但不执行**，
   能查出拼写错误、不存在的表、不存在的字段——这些客户端无从知道。

工具栏右上角会安静地显示状态：`检查中…` / `语法正确` / `N 处语法问题`。**只有出问题时才会展开
错误列表**，正确的查询不占地方。

两个实现上的取舍：

- **防抖 700ms 且丢弃过期响应**：每次按键都发请求会把服务端打满，而立刻检查会把刚打一半的词
  报成错误。用序号丢弃过期结果，避免慢响应盖掉新结果。
- **检查失败不冒充语法错误**：连不上服务端时显示「未能检查」，而不是把网络问题算在用户 SQL 头上。

检查在事务里进行且最后回滚，不留任何痕迹。

> 一个诚实的边界：PostgreSQL 的 `PREPARE` 只接受 `SELECT`/`INSERT`/`UPDATE`/`DELETE`/`VALUES`
> 这类语句，`CREATE TABLE` 之类无法预检。这类语句会被标记为「无法预检」而**不会**伪造一个语法
> 错误——把它当成语法错误会误导人。MySQL 则可以预检 DDL。

**编辑时有补全**：`⌘/Ctrl + 空格` 主动唤出，或直接输入时自动出现。补全内容包含 SQL 关键字
（按方言补充 `ILIKE` / `ON CONFLICT` / `AUTO_INCREMENT` 等）、**当前库的表名、视图名、
字段名**，以及**连接上的所有库名**。`↑↓` 选择、`Enter`/`Tab` 接受、`Esc` 关闭。
补全列表只提供真实存在的名字，不会替你改写没接受的文本。字段清单用一条 `information_schema`
查询取回，不是每张表一次往返。

**限定符补全带作用域**：输入 `x.` 时，`x` 会按 SQL 的作用域规则解析成对应的字段列表：

- `FROM users u` / `FROM users AS u` / `JOIN orders o` 里的别名都能用（`u.`、`o.`）
- 没有别名时表名本身也能用（`users.`），带库名的 `app.users` 也认
- **子查询里能取到父级的别名**（相关子查询就是这么写的），
  而**已结束的子查询里的别名不会泄漏到外层**，**兄弟子查询之间互不可见**
- 派生表（`FROM (SELECT id, name FROM users) x`）会从它的 select 列表推导出字段名，
  `u.id` 会归成 `id`
- 字符串和注释里写的 `FROM ... u` 不会被误认成别名

**SQL 控制台**：写 SQL、`⌘/Ctrl + Enter` 执行、`⌘/Ctrl + S` 保存。
临时查询的 `⌘/Ctrl + S` 会先问名字再写文件；已保存的查询直接覆盖原文件。
支持多语句，逐条显示结果——有结果集的显示表格，DML 显示受影响行数，出错则停在该条并显示服务端
原始错误。未保存时标签页标题带 `•`。

几个实现上的要点：

- **整个脚本在同一条连接的一个事务里执行**。这是 `USE` / `SET search_path` 能对每条语句都生效的
  前提（连接池里设置会话变量是不稳定的）；语句失败会中止后续语句，与客户端工具的行为一致。
- **列类型取自驱动返回的结果元数据**，不是从值的样子猜的——后者正是之前 TEXT 被读成十六进制的
  根因。能原生解码的类型（数字、文本、布尔、日期时间、JSON、二进制、**UUID**）按类型解码。
  类型名里的修饰符要额外处理：驱动把符号信息写在名字里（`BIGINT UNSIGNED`），
  而它携带的标志位是 crate 私有的，所以按后缀判断。
- **无法原生解码的类型不会让整条查询失败**，而是显示 `‹无法解码：INET›` 这样的占位符，
  并注明类型。目前 PostgreSQL 的 `inet` / 数组 / 范围 / 枚举属于这一类（已知限制）。
- **结果集按 1000 行分页**：执行时只取第一页，并多取一行用来判断「还有更多」；
  翻页时重新执行该语句并带上 `OFFSET`，所以任何时候内存里只有一页，几百万行的查询也不会卡住。
- **显示总行数**：结果超过一页时，后台异步跑一次 `COUNT(*)` 补上「共 N 行」。
  这一趟是实打实的开销（服务端要把整个结果算出来才能数），所以它**在首页显示之后才发起**，
  不会挡住你看到数据；数不出来时也不报错，只是不显示总数。
- **只写 `.xlsx`**：Excel 的两种格式上限不同——`.xlsx` 是 **1,048,576 行 × 16,384 列**，
  而 `.xls`（Excel 97-2003）只有 **65,536 行 × 256 列**。本工具只写 `.xlsx`（`.xls` 是另一套
  二进制格式：OLE2 容器里的 BIFF8），所以目标路径以 `.xls` 结尾时会**明确拒绝**，
  并说明该格式的真实上限，同时给一个「改为 .xlsx」的按钮——而不是把 xlsx 内容塞进 `.xls`
  让 Excel 打开时报格式不符。
- **导出带进度条**：导出对话框显示实时进度与「已写入 N 行」，并且可以取消。
  总行数已知时（导表、导出已统计过的查询）进度条是**确定百分比**，否则是不确定滚动条。
- **导出是整个结果，不是当前页**：点结果集上的「导出 Excel」，会**在服务端重新执行该查询并分页
  流式写入文件**，因此不受控制台分页限制。这也意味着**文件反映的是导出时刻的数据**，
  而不一定与屏幕上那一页完全一致——这是能导出任意行数必须付出的代价。
- 非查询语句（`SHOW` / `CALL` 等）无法重新包装执行，导出时退回到导出已取得的结果并说明。
- **执行前不显示结果区域**：没有结果就没有那一块，编辑器独占画面；执行后结果才出现。

### 5. 标签页

双击表 / 打开同步向导会新建标签页，同一个对象重复打开只会聚焦已有标签（按「连接 + 库 + 表」去重），
结构同步与数据同步各自只保留一个标签。

右键标签页：

| 菜单项 | 行为 |
| --- | --- |
| 关闭 | 关闭当前标签 |
| 关闭其他 | 只保留当前标签 |
| 全部关闭 | 关闭所有，并留下「欢迎」标签 |

中键单击标签也能关闭。**「全部关闭」不会留下空白窗口**——标签列表为空时总会有「欢迎」页兜底，
所以关闭按钮永远有东西可回退。

### 6. 数据网格（搜索 / 排序 / 编辑）

双击表进入数据网格，顶部工具栏与表头提供三件事：

**搜索条件**（服务端执行，不是只过滤当前页）：点「搜索条件」打开条件树。每个分组选择
「满足 **全部**（AND）或 **任一**（OR）条件」，分组可以**继续嵌套**，所以
`a = 1 AND (b = 2 OR c = 3)` 这类条件可以直接搭出来。支持 `=`、`≠`、`>`、`≥`、`<`、`≤`、
`包含`、`开头是`、`结尾是`、`在列表中`、`为 NULL`、`不为 NULL`。几个要点：

- **括号由嵌套结构生成**，不是让用户手写。嵌套分组一定带括号，最外层不带（`WHERE` 已经
  界定了范围），所以 `a OR b AND c` 这种优先级陷阱不会出现。
- **空分组不参与查询**：还没填完的分组会被忽略，既不会变成「匹配不到任何行」，
  也不会生成非法 SQL。嵌套深度上限 8 层。

- **值按列类型转换**：数值列比较的是数字而不是字符串，日期列接受多种写法并归一化；
  值不合法会在发出请求前报错（"abc 不是整数"）。
- **LIKE 通配符被转义**：搜索 `100%` 只匹配真的含有 `100%` 的行，不会匹配所有行。
- 选「=」却留空值时会提示改用「为 NULL」——`= NULL` 永远不匹配，静默返回空表会让人
  以为表里没数据。
- 状态栏显示**符合条件的总行数**，而不只是当前页的行数。

**列排序**：单击列头在 升序 → 降序 → 取消 之间循环。排序在服务端执行，并**自动附加主键
作为 tiebreaker**——否则排序值相同的行没有确定顺序，翻页会重复或漏掉行。真库测试专门断言了
带重复值时的分页序列。

**分页**：工具栏可选每页 **100 / 200 / 500 / 1000** 行，默认 1000。服务端硬上限就是 1000，
请求更大的页会被夹到 1000——一页塞更多行对渲染和内存都没有好处。

**列宽与列信息**：

- **列宽可拖动调整**：表头右边缘是拖拽把手，双击某一列的分隔线可让该列恢复按内容自动测量，
  工具栏「重置列宽」恢复全部。列宽按「连接 + 库 + 表」在本次会话内记住，切换标签页不会丢。
  首次打开时会根据列名和前 60 行内容估算宽度（中文按双宽计算）。
- **悬停浮框**：**列头和数据格都会浮出信息框**，都显示列名、类型、「主键 / 非空 / 生成列」
  标记和**列备注**（`COMMENT`）。没有备注的列会明确显示「该列没有备注」，而不是留空。
  悬停数据格时，浮框还会多出「本格的值」——网格里长值会被省略号截断，这里能看到完整内容
  （NULL 会写明是 NULL，而不是显示成空）。浮框有 220ms 延迟，避免鼠标移动时闪烁；
  靠近窗口底部时会自动翻到上方；滚动时自动消失，否则它会停在一个已经滚走的列上。
  进入单元格编辑时浮框会立即收起，不挡输入框。

**单元格编辑**：单击单元格直接进入编辑，`Enter` 提交、`Esc` 取消，失焦也会提交。

- **没有主键的表只读**：定位不到行就不该假装能改，状态栏会写明原因。
- **生成列不可编辑**，鼠标移上去会说明。
- 提交时生成的语句同时匹配**主键**和**你屏幕上看到的那个旧值**：

  ```sql
  UPDATE t SET col = 'new' WHERE id <=> 1 AND col <=> 'old';
  ```

  这是乐观锁。如果这行在你编辑期间被别人改过或删掉，语句匹配不到任何行，工具会明确提示
  「该行已被其他人修改或删除」，而不是默默覆盖别人的修改。NULL 用 `<=>`（MySQL）/
  `IS NOT DISTINCT FROM`（PostgreSQL）比较，所以「从 NULL 改成值」和「把值清成 NULL」
  都能正确匹配。
- 清空输入框写入 NULL；非空列不允许清空，会直接提示。

### 7. Excel 导入

右键表 → **导入** → **从 Excel 导入**，流程是「选文件 → 选工作表与表头行 → 配置列映射 → 选导入策略 → 导入 → 看结果」。

**解析**用 Rust 侧的 `calamine`（纯 Rust，支持 xlsx/xlsm/xlsb/xls/ods），而不是把解析库塞进
webview：前端体积不变，也不必依赖 npm 上已停止维护的 `xlsx` 包。单元格按类型还原——
数字去掉多余的 `.0`、布尔统一成 `true`/`false`、**Excel 日期序列号按单元格格式还原成日期**
（否则会存成 `45356` 这种数字）、空单元格是 NULL 而不是空串、损坏的公式会作为错误值暴露出来。

**值转换**按目标列的类型做，转不过去的值会明确指出原因，而不是当成字符串硬塞进去：

| 列类型 | 接受的形式 |
| --- | --- |
| 整数 | `42`、`42.0`（表格常把整数存成浮点）、`-7` |
| 小数 | 合法数字字面量，原样输出以保留精度（`DECIMAL` 不受浮点污染） |
| 布尔 | `true/false`、`1/0`、`yes/no`、`是/否`、`Y/N` |
| 日期 / 时间 | `2024-03-05`、`2024/3/5`、`2024-03-05 10:20:30`、RFC3339 等，统一归一化 |
| JSON | 先校验再写入，格式错误会报错而不是丢给服务端 |
| 文本 | 按方言转义 |
| 二进制 | 明确拒绝（暂不支持） |

**导入策略（最后一步选择）**：

| 策略 | 生成的语句 | 遇到已存在的行 |
| --- | --- | --- |
| **新增** | `INSERT INTO … VALUES …` | 主键冲突 → 报错，不覆盖 |
| **覆盖** | MySQL `INSERT … ON DUPLICATE KEY UPDATE`<br>PostgreSQL `INSERT … ON CONFLICT (主键) DO UPDATE` | 用 Excel 里的值更新该行 |

覆盖模式按**主键**匹配，主键列本身不参与覆盖。表没有主键时该选项不可选；主键未映射时会警告
「所有行都会按新增处理」。结果面板区分「其中覆盖 N 行 / 新增 M 行」——这个拆分是在写入前用
主键查一次得到的，只在整批成功时才报告，不拿估算值充数。

> 一个必须知道的差异：PostgreSQL 的 `ON CONFLICT (主键)` 只在主键冲突时触发，撞上其他唯一索引
> 会报错；而 MySQL 的 `ON DUPLICATE KEY UPDATE` 对**任何**唯一键都生效，可能更新到一行并非主键
> 相同的数据。用 MySQL 覆盖前请确认表上除了主键还有哪些唯一约束。

**几个刻意的设计**：

- **先全量校验再写入**：每一行都在写入前转换完毕，所以「第 4 行 amount 不是数字」这类问题在
  导入前就能看到，而不是写了一半才发现。
- **生成列不参与映射**，自增列可以不映射（由数据库生成）。
- **未映射的字段会说明会发生什么**：`将由数据库自增生成` / `将使用数据库默认值` / `将写入 NULL`。
  而非空且无默认值的字段没被映射时直接报错，不会逐批失败 200 次。
- **「跳过无法转换的行」可关**：关掉后遇到第一个坏值就停止，一行都不写。
- **事务**：默认整体事务，PostgreSQL 失败即整体回滚；MySQL 无法回滚，此时从失败处立即停止，
  并明确告知「失败批次之前的行已经写入」。批次按 200 行分组，可调。

### 8. Excel 导出

右键表 → **导出** → **导出 Excel**：勾选要导出的列、给每列改名（默认用列名）、用 ↑↓ 调整列在
表格里的顺序，再设置工作表名与行数上限，选好保存位置后导出。结果里会显示导出了多少行、
写到哪个文件。

**写入**用 `rust_xlsxwriter`（纯 Rust，不需要装 Office，也没有 C 依赖）。值的处理有一点很关键：

- **数值写成数值单元格**，不是文本，这样在 Excel 里能直接求和排序。小数能无损放进双精度时
  写成数值，**超过双精度位数的小数保留原文**——宁可不可计算，也不能悄悄丢位数。
- **布尔写成布尔单元格**，NULL 写成**空单元格**（而不是文本 "NULL"）。
- 日期、时间、JSON、二进制写成文本，语义明确，且能被导入功能原样读回。

**读取**按主键用键集分页（`WHERE key > 上次的 key`），不是 `LIMIT/OFFSET`——否则导出大表时
偏移越深越慢，整体是平方级。表没有可用主键时退回 `LIMIT/OFFSET`。

Excel 单表上限 1,048,576 行，达到上限会截断并在结果里明确告知，不会假装导完了。

### 9. 结构同步

1. 工具栏「结构同步」
2. 左侧选 **源（结构基准）**，右侧选 **目标（将被修改）**
3. 「开始对比」→ 得到差异树
4. 勾选要应用的变更（默认已排除所有删除类操作）
5. 「预览 SQL」检查 DDL，或直接「执行同步」

支持的操作：

| 类别 | 支持 |
| --- | --- |
| 表 | 新建表、删除表 |
| 列 | 新增、删除、修改（类型 / 可空 / 默认值 / 自增 / 注释 / 字符集 / 生成列表达式） |
| 主键 | 新增、删除、修改 |
| 索引 | 新增、删除、修改（含唯一性） |
| 外键 | 新增、删除、修改（含 ON DELETE / ON UPDATE） |
| 视图 | 新增、删除、修改定义（同类型数据库之间；跨类型会被拒绝） |
| 物化视图 | 同上，PostgreSQL 使用 `CREATE MATERIALIZED VIEW ... WITH DATA` |
| 自定义类型 | PostgreSQL `ENUM` / `DOMAIN`：新建、删除；枚举加值（含位置）、域的可空/默认值/CHECK 约束修改 |

执行顺序经过设计以避免依赖冲突：
先删除失效外键 → 删除表 → 创建表（含主键）→ 删除索引 → 修改主键 → 删除列 → 修改列 → 新增列 → 新增索引 → 新增外键。

### 10. 数据同步

1. 工具栏「数据同步」
2. 选源表与目标表（可跨库、跨数据库类型）
3. 「开始对比」→ 得到新增 / 修改 / 删除统计与逐行明细
4. 选择要执行的动作（**删除默认关闭**），可选是否使用事务
5. 「预览 SQL」或「执行同步」

匹配规则：默认使用**目标表主键**，并要求源表存在同名字段；字段映射默认按同名自动建立。
对比字段必须非空（主键天然满足）。

**流式对比**：两侧都按主键排序、用 keyset 分页逐页读取并做归并 join，内存占用与表大小
无关（只与差异行数相关），因此**不再有比较行数上限**。排序统一强制为字节序
（MySQL `CAST(col AS BINARY)`、PostgreSQL `COLLATE "C"`），所以即使两端表的 collation
不同（例如 `utf8mb4_general_ci` 对 `utf8mb4_bin`），归并也不会错位。

### 关键设计

**归一化结构模型**：MySQL 的 `information_schema` 与 PostgreSQL 的 `pg_catalog` 各自被读取为
统一的 `TableStructure`（列 / 主键 / 索引 / 外键），对比与 DDL 生成只处理这一种模型，
两个引擎共用同一套代码路径。

**视图依赖处理**：视图定义里的 schema 限定会被重写到目标库（否则目标视图会去读**源库**的表——
两边数据一致时完全看不出来）。当某张表发生变化时，依赖它的视图（含未被勾选的、以及视图套视图的
情况）会先按逆依赖序删除、再按依赖序重建，因为 PostgreSQL 不允许直接修改被视图引用的列。

**职责边界：结构同步只改结构，数据同步只改数据。**
结构同步永远不会向现有行写入任何值——包括看起来「顺手」的占位值回填。因此向已有数据的表添加
「非空且无默认值」的列时，PostgreSQL 会拒绝那条 DDL，工具就让它失败（见下面的失败即回滚），
只给出一条提示，告诉你该怎么分步处理：

```
1. 结构同步：把该列先同步为「可空」        （纯结构，不写任何行）
2. 数据同步：写入真实值                    （纯数据）
3. 结构同步：再同步一次，加上 NOT NULL      （纯结构）
```

**失败即回滚**：结构同步默认把整个 DDL 计划包在一个事务里，任何一条失败——或用户中途取消——
都会整体回滚，目标库保持原样。PostgreSQL 支持 DDL 事务；**MySQL 的 DDL 会隐式提交，无法回滚**，
此时执行会在第一条失败处立即停止，并明确告知「已执行的变更无法回滚、剩余语句未执行」，
不会假装回滚成功。这个差异通过 `transactional` 标志一路传到界面上。

**自定义类型（仅 PostgreSQL）**：`ENUM` 与 `DOMAIN` 会先于使用它们的表创建、晚于引用它们的表删除。
枚举只支持增加值（PostgreSQL 本身不支持删除枚举值）；域的基础类型变更同样不支持，这两种情况
会明确告警而不是生成无法执行的 DDL。列上的自定义类型会被**显式限定 schema**，因为目标 schema
不一定在连接的 `search_path` 里。

**物化视图刷新**：PostgreSQL 的物化视图在创建时快照数据，所以数据同步完成后会自动
`REFRESH MATERIALIZED VIEW`（可在界面上关闭），否则它会一直读到创建那一刻的旧数据。

**生成列保真**：MySQL 的 `STORED` / `VIRTUAL GENERATED` 与 PostgreSQL 的
`GENERATED ALWAYS AS (...) STORED` 会被识别并原样重建。数据同步把这些列排除在
INSERT / UPDATE 之外（值由目标端自己计算），因此既不会被降级成普通列，也不会被服务端拒绝。

**值解码**：不依赖驱动的结果集类型推断，而是使用内省得到的列类型决定如何解码；
PostgreSQL 上驱动无法原生解码的类型（`uuid`、`inet`、数组、枚举、域等）会自动以
`col::text` 取出，避免整个查询失败。

**字面量而非绑定参数**：DML 由生成的字面量构成，因此「预览 SQL」与实际执行的内容
完全一致；转义按方言分别处理（MySQL 转义反斜杠，PostgreSQL 用标准 `''` 并转义 NUL）。

**计划缓存**：对比结果缓存在后端（结构对比与数据同步各一份）。预览与执行使用同一份
快照，避免两次计算之间数据变化导致执行内容与预览不符。

**启动降级**：配置目录不可写时回退到临时目录、主密钥无法持久化时使用临时密钥，
两者都会在界面上给出警告，而不是让应用启动失败。

### 真实数据库端到端测试

```bash
cp .env.live.example .env.live    # 填入 host / port / user / password
./scripts/run-live-tests.sh
```

测试会走完应用使用的同一条代码路径（内省 → 对比 → 生成 DDL/DML → 执行），
并在服务器上创建再删除名为 `datasync_live_*` 的临时库 / 模式。

> **不会碰线上库**：`create_namespace` / `drop_namespace` 带有一条断言，任何不以
> `datasync_live_` 开头的名字都会直接 panic。因此即使测试写错了名字，也只可能失败，
> 不可能删掉同一个服务器上的真实库。

1. 在源端建两张表，覆盖主键、唯一键、索引、外键、JSON、BLOB、布尔、DECIMAL、
   DATETIME 以及 STORED 生成列
2. 空目标端对比 → 生成 DDL → 执行 → 再对比，断言「已完全一致」
3. 源端制造结构漂移（加列 / 加宽列 / 删列 / 改类型 / 加索引 / 改默认值）→ 同步 → 再断言一致
4. 源端插入数据 → 数据同步 → 再对比断言 0 新增 / 0 修改 / 0 删除
5. 源端 UPDATE + DELETE → 再同步 → 再断言一致
6. 断言目标端的生成列被真正重算（`amount * 2`），而不是被拷贝或留空
7. 源端建视图、视图套视图、PostgreSQL 物化视图 → 同步 → 断言目标端视图可查询、
   不引用源库、且行数与源端一致（物化视图需正确刷新）
8. PostgreSQL：建 `ENUM` 与 `DOMAIN`、并在表上使用该枚举 → 同步 → 断言枚举值、
   域的基础类型与 CHECK 约束都到了目标端；漂移阶段给枚举加值 → 再断言已传播
9. 数据同步完成后，往源表加一个**可空**列并写入真实值 → 结构同步 → 断言目标端
   只多了一个可空列，且**现有行全部仍是 NULL**（结构同步没有写任何行数据）
10. 数据同步 → 断言该列被真实值回填
11. 源端把该列收紧为 NOT NULL → 结构同步 → 断言约束已应用且数据未受影响
12. 表数据浏览：分页、`has_more`、列 kind 与网格对齐、PostgreSQL 的
    `uuid` / `inet` / `text[]` / 枚举等需 `::text` 转换的类型、MySQL 的 TEXT 列
13. PostgreSQL 失败即回滚：计划里第一条语句会成功、第二条必然失败 → 断言整体回滚
    （连成功的那个变更也不留）、数据未动；同一计划在关闭事务时则留下第一条的变更，
    以此证明这个开关确实在起作用。MySQL 侧断言 `supportsTransactionalDdl` 为 false
14. 新建表：按设计生成 `CREATE TABLE` 并执行 → 断言主键与非空约束按设计建立；重复建表、
    主键指向不存在的字段都在执行前被拒绝
15. 表级操作：加字段 + 字段改名（断言走重命名、**数据保留**、不产生删表语句）、
    索引增删（断言复合索引列顺序保留、唯一约束保留、**外键支撑索引不会被删除**、
    MySQL 上用一个覆盖外键的索引替换原索引能成功执行）、重命名表、
    外键增删（断言引用表与 `ON DELETE` 动作保留、两端字段数不一致被拒）、
    重命名表、删除被引用的表（断言外键先被解除、未选中的表保留）
16. 删除仍被引用的表：目标端两张表互相引用形成环，另有一张待删表被「未勾选变更」的表引用
    → 断言所有外键先于表删除，且计划能真正执行成功
17. Excel 导入：用仓库里的 xlsx 夹具真导入 → 断言 **Excel 日期序列号还原成日期**、
    含引号的字符串完整写入、空单元格是 NULL、非法的第 4 行被跳过并记录行号与列名
18. 数据网格：搜索条件（含 `%` 字面量转义、数值比较、为 NULL、IN、多条件 AND、非法值拒绝）、
    升降序排序、**排序值相同时分页不重不漏**；单元格编辑（普通修改、旧值不匹配时拒绝写入、
    清空写入 NULL、从 NULL 改回值、非空列拒绝清空、类型不符报错）
19. 列备注：给列加上 `COMMENT`（PostgreSQL 用 `COMMENT ON COLUMN`）→ 断言它出现在网格的列
    元数据里（表头浮框的数据来源），且没有备注的列为空
20. 结果集分页与全量导出：造 2250 行（超过两页）后断言——首页恰好一页且提示还有更多；
    逐页读完恰好覆盖全部行且不重复（3 页）；可从任意 offset 读末页；
    导出写入的行数与真实行数一致（**不是只导当前页**）；回读生成的文件核对行数
21. 执行计划：分析 SELECT 与 UPDATE 都成功并返回计划行；**断言分析后数据未被改动**
    （这正是用 EXPLAIN 而非 EXPLAIN ANALYZE 的原因）；DDL 被标为「不支持分析」而不是报错
22. SQL 语法检查（自动检查走的同一条后端路径）：合法语句通过；关键字拼错、字段不存在都被服务端发现并带回原始错误；
    检查后**数据未被改动**；多语句逐条检查；DDL 在 PostgreSQL 上被标为「无法预检」
    而不是报成语法错误，且检查过程不会真的建表
23. Excel 导出：把表导出成 xlsx，**再用导入用的同一个读取器读回来**断言——重命名后的表头、
    中文、含引号的字符串、数值仍是数值、布尔仍是布尔、**NULL 是空单元格**、日期可读；
    另断言只导出选定列、工作表名生效、行数上限截断被标记、未知列在写文件前就被拒绝
24. SQL 控制台：执行 SELECT 断言结果集与列类型（由驱动元数据推导，不是猜的）、执行 DML 断言
    受影响行数、多语句按序执行且后续语句能看到前面的结果、出错停在出错那条并保留服务端错误、
    未限定表名能在指定库中解析（证明会话库名生效）；PostgreSQL 侧另外断言 inet/数组显示为
    带类型名的占位符、UUID 正常返回
25. 导入策略：改掉目标表里的值再以**覆盖**模式导入同一份数据 → 断言行数不变、被改动的值
    写回、`existingKeys` 为 3；再以**新增**模式导入同一份数据 → 断言主键冲突而失败；
    最后构造批次中途失败 → PostgreSQL 断言整体回滚、MySQL 断言无法回滚但提示准确

**跨类型同步被正确拒绝**。

未配置 `.env.live` 时这些测试会自动跳过，`cargo test` 仍然全绿。

## 已知限制

- 只支持 MySQL 与 PostgreSQL；外部表会被跳过并提示
- 表索引页签不支持前缀索引（`col(10)`）与函数索引的编辑，这类索引会原样保留但显示为只读
- 视图同步不保留 `DEFINER` / `SQL SECURITY` / `ALGORITHM`，会以当前用户重建
- 数据同步的**差异语句**会全部保留在内存中以便「预览即执行」；差异行数极大时内存随之增长
- 不支持跨类型同步（见开头说明），两端必须是同一引擎
- 不支持删除 PostgreSQL 枚举值、修改域的基础类型（引擎本身不支持），会告警提示手工处理
- MySQL 的 `SET` 类型仍按普通文本处理
- 分区表按普通表处理
- SQL 控制台中 PostgreSQL 的 `inet` / 数组 / 范围 / 枚举等类型显示为 `‹无法解码：类型›`
  占位符（不会失败，但看不到值）；MySQL 的数值类型即使映射漏了也会退化成数字文本，
  不会变占位符
- 语法检查在 PostgreSQL 上无法覆盖 DDL（`PREPARE` 不支持），这类语句会提示「无法预检」
- 高亮是词法级的，不做语法分析：关键字出现在字符串或注释里不会被误判，但别名等
  上下文相关的着色没有处理
- 别名补全只解析 `FROM` / `JOIN` 一层结构：CTE（`WITH x AS (...)`）的名字、`UPDATE ... FROM`、
  存储过程等场景没有覆盖
- 执行计划只用 `EXPLAIN`（不执行）；想要 `EXPLAIN ANALYZE` 的真实耗时需要另行确认，
  因为它会真的跑一遍语句
- 控制台把整个脚本包在一个事务里，因此 PostgreSQL 上长时间运行的脚本会一直占着事务
- Excel 导入不支持二进制列；CSV 导入 / 导出尚未实现（菜单项已占位）
- Excel 导出只写单个工作表，不做多表拆分；超过 1,048,576 行会被截断并提示
- 覆盖模式下 MySQL 的 `ON DUPLICATE KEY UPDATE` 会被任意唯一键触发，与 PostgreSQL 的按主键匹配语义不完全一致
- 真库测试只创建/删除 `datasync_live_*` 命名空间，并有断言强制这一点：任何试图操作其它名字
  都会直接失败，以免误伤同一台服务器上的真实库
- 未做公证（notarization）：别人首次打开可能被 Gatekeeper 拦截，右键「打开」即可，
  或 `xattr -d com.apple.quarantine "/Applications/DataSync Studio.app"`
- 应用为 ad-hoc 签名（本机可用，不满足分发要求；正式分发需要开发者证书 + 公证）
